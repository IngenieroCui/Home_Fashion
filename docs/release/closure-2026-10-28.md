## Correcciones

### H03 - Inventario de entrega

- La reserva existente incrementa `quantityReserved` sin modificar `quantityOnHand`.
- `DeliveriesService.complete` agrupa por variante las cantidades IN_STOCK aún no entregadas, bloquea las variantes por id ascendente y descuenta **onHand y reserved juntos**.
- El consumo, estados de ítems, cierre del pedido y evidencia de entrega comparten una transacción. Una excepción revierte todas esas escrituras.
- MADE_TO_ORDER no reserva ni consume inventario terminado, incluso cuando referencia una variante de catálogo.
- La entrega repetida se rechaza con el contrato actual de estado inválido; no descuenta de nuevo. Dos completaciones concurrentes producen un único éxito y un único consumo.
- Reservas insuficientes o inconsistentes producen conflicto sin cambios parciales. No se corrigen automáticamente inconsistencias históricas.
- Creación e inicio/completación/cancelación usan pedido antes de entrega; los ítems y variantes se bloquean en orden ascendente. La lectura inicial de entrega solo resuelve el orderId inmutable; las decisiones se toman tras los locks.

### H04 - Cotizaciones

- `updateQuote`, `addItem`, `updateItem`, `deleteItem` y `changeStatus` adquieren primero un lock UPDATE de la cabecera dentro de su transacción y revalidan el estado después de obtenerlo.
- Los ítems se leen/bloquean después de la cabecera. La conversión usa consultas explícitas cabecera -> ítems por id -> venta, sin un join que mezcle el orden de locks.
- La cabecera, detalle, auditor de modificación y recálculo son atómicos. Una sustitución fallida conserva el ítem original.
- Una edición que espera a una aceptación se rechaza al ver ACCEPTED. Tampoco puede cancelar ni modificar una cotización aceptada.
- La conversión sigue siendo única y copia los snapshots/precios/cantidades cotizados, aunque después cambie el catálogo.

## Migraciones y compatibilidad

Hay **15 migraciones** en fuente. H03/H04 requieren **cero migraciones nuevas**. Las dos adiciones ya presentes por H05/Wompi son:

1. `20261028000000-payment-intentions.ts`: columnas nullable `intent_id`, `intent_fingerprint` e índice único `uq_sale_payment_intent`; conserva pagos históricos con intención null.
2. `20261028001000-payment-attempts.ts`: tabla `payment_attempts`, referencias e invariantes exclusivas de Sandbox/COP.

Ambas declaran `down` forward-only. MySQL DDL hace commits implícitos: no se promete rollback transaccional de esquema. La migración PaymentAttempt no ofrece recuperación genérica de un DDL parcialmente aplicado; revisar `SequelizeMeta`, tabla, índices y constraints antes de reintentar. Se comprobaron las 15 en la instancia descartable. **El estado actual de Aiven no se consultó ni se supone actualizado.**

Primero debe revisarse el estado remoto y autorizarse cualquier migración. Desplegar código H05 contra un esquema anterior de 13 migraciones es incompatible. Clientes que registran nuevos pagos manuales deben enviar el UUID `intentId`; el frontend actual ya lo hace. Una edición o transición que pierde la carrera se rechaza según los contratos existentes (400/409 según operación); no se reintentan mutaciones automáticamente.

Al revertir el código H03 se reintroduce el defecto de consumo. No deshacer las migraciones financieras ni borrar intenciones/intentos. Las entregas ya cerradas antes de esta corrección conservan sus datos: conciliación histórica requeriría un trabajo independiente y autorizado, nunca un backfill automático de esta release.

5. Medios accesibles por URL, ausencia de flujo completo de cancelación de taller y otros hallazgos críticos ajenos a H03/H04/H05 conservan el estado de la auditoría; usar datos sintéticos en demo.

## Repetir las pruebas dirigidas

En una copia limpia del paquete, con Node/pnpm y dependencias del lockfile instaladas:

```powershell
pnpm install --frozen-lockfile
pnpm --filter @home-fashion/shared build
pnpm --filter @home-fashion/api build
node tests/e2e/support/local-mysql.mjs
pnpm test:closure
pnpm --filter @home-fashion/api exec jest --config jest.payments.config.cjs --runInBand
pnpm --filter @home-fashion/api exec tsc -p tsconfig.payments-tests.json
pnpm --filter @home-fashion/web test
pnpm --filter @home-fashion/web build
```

El provisioner usa el binario MySQL 8.4 instalado en Windows y el puerto 33307. No reutiliza el servicio Windows. Si hay `.env.e2e` o el puerto está ocupado se bloquea; no cambiarlo para apuntar a Aiven. Cada copia limpia genera sus secretos locales. Antes de cualquier escritura el harness valida host, puerto, nombre dedicado, UUID, datadir y marcador. No cargar `.env` productivo. El informe específico queda en `.e2e-results/payments/closure-results.json`; el unitario se puede exportar con Jest `--json --outputFile=...`.

Para el navegador, arrancar primero la web compilada en otra terminal con `API_SERVER_URL=http://127.0.0.1:3301/api`, `NEXT_PUBLIC_API_URL=http://127.0.0.1:3301/api` y `pnpm --filter @home-fashion/web exec next start -H 127.0.0.1 -p 3300`. Después ejecutar `node tests/payments/sandbox-directed.cjs --browser`. Este harness levanta Nest en 3301 y simula el proveedor; su informe declara esa limitación. Detener la web al terminar y ejecutar `node tests/e2e/support/local-mysql.mjs --stop` para MySQL.

## Venta completa para demostración (5-7 minutos)

Usar una base aislada migrada, catálogo y cuentas sintéticos ADMIN/WORKSHOP, API/web locales y Cloudinary de prueba si se van a subir fotografías. Preparar variantes con `onHand=10`, `reserved=0` y precio $100.000. Mantener Wompi deshabilitado si no hay credenciales test; el pago manual permite completar el recorrido. El script dirigido crea fixtures propios, pero **no deja un entorno de demo atendido** después de terminar.

1. ADMIN crea cliente sintético y cotización con 2 unidades IN_STOCK de una variante y 1 unidad MADE_TO_ORDER de otra; total $300.000, sin domicilio adicional. Enviar QUOTED, registrar aceptación y convertir una sola vez a venta. Intentar editar después de aceptar debe rechazarse.
2. Registrar anticipo manual $100.000 con intención nueva; comprobar saldo $200.000. Para demostrar timeout con certeza usar el test `--browser`: provoca pérdida de respuesta tras commit, reload y reenvío sin duplicar. No simular un segundo pago manual con UUID nuevo.
3. En la venta seleccionar Crear pedido; enviar todas las líneas una vez mediante `POST /api/admin/orders/from-sale/:saleId`. Clasificar stock/fabricación. Comprobar variante de stock `10/2` (onHand/reserved), variante de fabricación `10/0`.
4. Asignar la línea MADE_TO_ORDER a WORKSHOP en `POST /api/admin/workshop-jobs`. Como taller enviar STARTED, PROGRESS y READY_FOR_REVIEW por el flujo web/API o Android si su entorno está validado. Flutter usa `POST /api/workshop/jobs/:id/progress-media`; la API JSON `/progress` permite una demo controlada sin upload.
5. ADMIN revisa y aprueba el último reporte por `POST /api/admin/workshop-progress/:id/review`. La línea fabricada queda READY. Generar seguimiento privado si se quiere mostrar al cliente; compartir solo el enlace sintético durante la demo.
6. Programar entrega por `POST /api/admin/deliveries`, asignar conductor/fecha y comenzar con `POST /api/admin/deliveries/:id/start`; todas las líneas activas deben estar RESERVED/READY.
7. Completar con receptor y 1-5 evidencias URL sintéticas válidas (`.../:id/complete`) o fotografías (`.../:id/complete-media`). Comprobar DELIVERED, pedido COMPLETED, variante stock `8/0` y variante fabricada `10/0`. Repetir complete debe rechazar sin cambios de cantidades.
8. Registrar saldo manual $200.000 con una intención distinta. Confirmar pagado $300.000, saldo cero y dos movimientos. Entrega y pago son cierres independientes; no se introduce una regla nueva que obligue a cobrar antes de entregar.

Si se incluye Wompi, anunciar explícitamente “Sandbox simulado” en la explicación de la demo y usar la prueba dirigida. Una demostración externa exige las llaves test y HTTPS documentados en `docs/payments/INSTRUCCIONES_SANDBOX.md`; no afirmar que el sistema procesa pagos reales.
