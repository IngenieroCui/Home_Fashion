# Revisión técnica y de interfaz — 4 de septiembre de 2026

La revisión toma `tesis.md` como referencia del negocio. Conserva el monolito modular, los actores y el recorrido del MVP. No se creó una base de datos, no se ejecutaron migraciones ni se realizó un despliegue: el propietario confirmó que aún no existe configuración local para una primera prueba manual.

## Correcciones realizadas

| Hallazgo | Resultado y evidencia |
| --- | --- |
| Next no iniciaba por parámetros dinámicos incompatibles (`id`/`saleId`) en pagos | Se unificó la ruta como `/api/admin/sales/[id]/payments/[paymentId]/void`; el servidor de producción inicia correctamente. |
| Respuestas antiguas reemplazaban filtros recientes en listados | Clientes, cotizaciones, ventas, pedidos, trabajos, avances y entregas comparten carga cancelable; una solicitud anterior no actualiza la nueva vista. Se limpian datos obsoletos, se valida la respuesta y se permite reintentar. |
| Cookies de sesión vencida se borraban en una respuesta distinta de la enviada | La redirección al acceso lleva la eliminación de cookies. Una caída temporal del servicio conserva la sesión y muestra un aviso sin bucle de redirecciones. |
| Renovación duplicada y pérdida de tokens tras una caída de la API | Los handlers comparten un proxy de sesión; la renovación se coordina por sesión dentro de un proceso Next y las nuevas cookies se conservan aunque falle la operación siguiente. Pruebas en `apps/web/test/regressions.test.cjs`. |
| Destino de redirección demasiado permisivo | El retorno de sesión solo permite rutas del panel del mismo origen. Pruebas con URL externa, doble barra, barra inversa y caracteres de control. |
| Errores de API visibles en inglés o con detalles internos | Traducciones explícitas y mensajes generales en español; los fallos de red en escrituras explican que debe comprobarse si la operación se guardó. No se reintentan escrituras automáticamente. |
| Editar otra categoría o elemento conservaba el formulario anterior | Cada edición se identifica por el registro seleccionado; el selector de variantes se reinicia cuando cambia el producto. |
| Personalización de una variante y detalles de una solicitud pública no eran editables de forma consistente | La cotización conserva los detalles solicitados y permite personalización en productos que la admiten, incluso con variante. Las etiquetas del taller están en español. |
| Precio público redondeado y datos incompletos tratados como cero | Se conservan centavos, se excluyen variantes inactivas y se muestra un mensaje cuando el precio está pendiente. |
| Campos arbitrarios de personalización llegaban al seguimiento público | La API publica únicamente campos de personalización reconocidos y valores simples; excluye datos financieros, internos y objetos anidados. Prueba de regresión de `OrderTrackingService`. |
| Conflicto de idempotencia sin salida en la solicitud pública | Se permite preparar explícitamente otra solicitud; el reintento normal mantiene la clave original para evitar duplicados. |
| Patrón de teléfono incompatible con validación HTML moderna | Se escaparon los caracteres reservados de la expresión del formulario. |

## Interfaz

- Portada con jerarquía tipográfica, composición editorial y fotografía real del catálogo cuando existe.
- Catálogo con mensajes distintos para colección vacía, filtros sin resultados y servicio no disponible.
- Panel con módulo activo, navegación móvil antes del contenido, acceso rápido al contenido mediante teclado y tarjetas con descripciones operativas.
- Formularios, tablas, botones deshabilitados, avisos y seguimiento con una presentación coherente; ajustes para pantallas estrechas y preferencia de movimiento reducido.
- Pantallas generales de error, ruta inexistente y carga del panel; controles para reintentar consultas.
- Flutter con tema actualizado y localización `es-CO`, incluidos controles y mensajes estándar de Material.

## Límites y siguiente validación

No se puede afirmar todavía que el recorrido catálogo → solicitud → venta → fabricación → entrega funcione de punta a punta. Falta configurar MySQL y la API, ejecutar el [smoke test del MVP](smoke-test-mvp.md), inspeccionar las pantallas en navegador y probar Android contra la API real. No hubo navegador conectado durante esta revisión, por lo que los cambios visuales no cuentan aún como inspección visual aprobada.

La coordinación de renovación web es local a un proceso Next. Antes de ejecutar varias réplicas debe revisarse la coordinación entre procesos. Las respuestas tras interrupciones de red en escrituras deben verificarse en el listado o detalle antes de repetir una operación.

No hace falta alojar el sistema para la primera prueba: basta MySQL, la API y Next ejecutándose localmente. Consulta [Desarrollo](development.md) y [Smoke test](smoke-test-mvp.md) para preparar una base descartable y los actores de prueba. Las credenciales se configuran en `apps/api/.env`; `apps/web/.env.local` contiene las URLs locales. Android usa `API_BASE_URL`.
